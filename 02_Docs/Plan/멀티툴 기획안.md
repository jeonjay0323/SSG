# 멀티툴 기획안

> 참여형 창작 설치물. `01_Product/MultiTool` 로 구현돼 배포 중이다.
> 기술 문서는 [01_Product/MultiTool/README.md](../../01_Product/MultiTool/README.md).

---

## 1. 한 문장

> **참여자가 폰으로 한 문장을 보내면, 그 문장이 영상 장면이 되어 앞 장면에 이어 붙는다.**

세 이야기가 큰 화면에서 동시에 굴러가고, 6씬이 차면 하나의 웹드라마가 완성된다.

---

## 2. 왜 이 형태인가

슥의 주장은 **"원고를 넣으면 영상이 된다"** 이다.
현장에서 이 주장을 증명하는 방법은 두 가지다.

| 방법 | 참여자가 보는 것 | 문제 |
|---|---|---|
| 완성된 영상 상영 | 잘 만든 결과물 | **미리 만든 것과 구분되지 않는다.** 주장이 증명되지 않음 |
| **참여자 입력 → 즉석 생성** | 방금 내가 쓴 문장이 영상이 되는 것 | 생성 시간을 견뎌야 함 |

두 번째를 골랐다. **"미리 만든 게 아니다"** 를 참여자가 스스로 확인할 수 있는 유일한 형태이기 때문이다.
그래서 이 설치물의 모든 설계는 **생성 시간을 어떻게 견디게 할 것인가**로 수렴한다.

### 2.1 왜 '한 문장'인가

| 요구 크기 | 결과 |
|---|---|
| 한 문단 이상 | 아무도 안 쓴다. 현장에서 글을 쓰게 만들 수 없다 |
| **한 문장 (40자)** | 부담은 없는데 "내가 썼다"는 소유감은 남는다 |
| 선택지 고르기 | 소유감이 없다. 내 문장이 아니다 |

### 2.2 왜 '이어 만들기'인가

각자 따로 영상을 만들면 **참여자 수만큼 비용이 들고, 남는 것은 파편뿐이다.**
이어 붙이면 참여자가 늘어도 이야기는 하나로 모이고, 6씬이 차면 완결된 결과물이 남는다.

---

## 3. 참여자 경험

```
폰으로 접속 → 이야기 고르기 → 이름 정하기 → 한 문장 쓰기
                                              ↓
        큰 화면에 내 문장이 즉시 뜬다  ←───────┘
                                              ↓
              [다른 사람도 보냈으면] 투표
                                              ↓
                      영상이 이어 붙는다
```

| 단계 | 폰 화면 | 큰 화면 | 소요 |
|---|---|---|---:|
| 1 | 이야기 고르기 | 도입부 반복 재생 | — |
| 2 | 이름 정하기 (건너뛸 수 있음) | | — |
| 3 | 한 문장 쓰기 | | — |
| 4 | 보냈습니다 | **내 문장이 접수함에 뜬다** | 즉시 |
| 5 | 만드는 중 | 리스테이징된 첫 프레임 선공개 | 약 45s |
| 6 | 투표 (동시 참여 시) | 후보 영상 + 실시간 득표 | 60s |
| 7 | 발표 | 채택본이 이어 붙는다 | 10s |

**핵심은 4번이다.** 영상은 45초 뒤지만 *내 흔적*은 1초 만에 공개된다.
이탈을 막는 것은 사실상 이 장치다.

---

## 4. 세 세계

동시에 세 이야기를 굴린다. 트랙이 하나면 앞사람 라운드가 끝날 때까지 아무도 참여할 수 없다.

| 이야기 | 매체 | 도입 |
|---|---|---|
| **이세계 용사** | 애니메이션 | 눈을 뜨니 낯선 숲. 발밑에 빛나는 소환진 |
| **야근** | 실사 (괴담 톤) | 새벽 세 시, 아무도 없는 사무실. 복사기가 혼자 돌아간다 |
| **게이트** | 웹툰 | 도심 한복판에 등급 미측정 게이트가 열렸다 |

**매체를 셋으로 나눈 것은 사용자 테스트에서 나왔다.**
창작의 토대로 사람들이 **가장 먼저 정한 것이 그림체**였다 — 실사인가 애니메이션인가.
줄거리도 인물도 아니었다 ([솔로툴 사용자 테스트 §3](../Research/솔로툴%20사용자%20테스트.md)).

부수 효과로 멀리서도 "세 개가 다르게 돌아간다"가 읽혀 사람이 다가온다. 동시에 [독자 리서치](../Research/잠재%20사용자%20리서치.md)의 가설 2
— 양식화된 매체가 실사보다 거부감이 적다 — 를 한자리에서 비교할 수 있다.

연출은 전부 `config/worlds/*.json` 에 있다. **코드에 프롬프트가 없다.**

## 5. 라운드 구조

라운드는 시계가 아니라 **첫 제출**로 시작한다.

| 단계 | 시간 | 내용 |
|---|---:|---|
| 접수 | 15s | 첫 문장이 들어오면 창이 열린다 |
| 생성 | 약 45s | 접수 마감 후. 프리스테이징으로 일부는 이미 끝나 있다 |
| 투표 | 60s | **2명 이상 참여했을 때만** |
| 발표 | 10s | 채택본 확정 |
| 완결 | 25s | 6씬이 차면 |

| 항목 | 값 |
|---|---:|
| 문장 길이 | 40자 |
| 한 이야기 분량 | 6씬 |
| 후보 수 | 3개 |
| 클립 | Veo 3.1 lite · 4초 · 9:16 |

**투표가 비용을 끊는다.** 참여자가 늘어도 최종 채택은 하나뿐이라,
생성 비용이 참여자 수에 비례하지 않는다.

## 6. 기술 구조 — 세 가지 발명

현장에서 쓰려면 **얼굴이 유지되고, 장면이 이어지고, 엉뚱한 입력을 견뎌야** 한다.

앞의 두 가지는 모델 제약에서 나온 과제가 아니라 **솔로툴 사용자가 한 말**에서 나왔다.

| 들은 말 | 만든 것 |
|---|---|
| "내가 생각했던 주인공 얼굴과 다르다" | 리스테이징 |
| "입력한 문장과 영상의 싱크가 안 맞는다" | 문장 해석 · 체이닝+트리밍 |
| "더 상세하게 편집할 수 없을까" | **미해결** — 방향이 '가볍게'로 틀어지며 의도적으로 접었다 |

### 6.1 리스테이징 — 얼굴 고정

Veo 는 시작 프레임과 인물 레퍼런스를 **함께 받지 못한다**
(`Image and reference images cannot be both set`).

그래서 인물 고정을 Veo 가 아니라 **이미지 모델 단계**에서 한다.

```
앞 클립의 마지막 프레임  +  배우 레퍼런스
            ↓  gemini-2.5-flash-image
   얼굴이 교정되고 앵글이 바뀐 '다음 컷의 첫 프레임'
            ↓
          Veo 3.1
```

| | 주기 |
|---|---|
| 얼굴 교정 | **매 씬** |
| 앵글 변경 | `restageEvery` 주기 |

둘을 한 스위치로 묶으면 앵글을 유지하는 씬에 레퍼런스가 안 들어가 얼굴이 세대마다 밀린다.

### 6.2 체이닝 + 트리밍 — 장면 잇기

시드 프레임을 클립 중간에서 뽑으면, 클립은 끝까지 재생되는데
다음 씬은 그 앞 상태에서 시작해 **되감기처럼 보인다.**

시드 지점에서 클립을 잘라 **클립의 끝 = 다음 씬의 시작**을 맞춘다.

### 6.3 문장 해석 — 입력을 견디기

참여자 문장을 그대로 넘기면 두 가지가 깨진다.

| 입력 | 그대로 넘기면 | 해석 후 |
|---|---|---|
| "안녕" | 화면에 **글자로 렌더된다** | 세계 안의 작은 사건으로 치환 |
| "지하철이 왔다" (판타지 숲) | 세계 밖 물체가 그대로 등장 | 의도를 유지한 채 세계 안 사물로 |

자막에는 **원문을 그대로** 띄운다. 해석은 뒤에 숨고 소유감은 지킨다.

## 7. 무인 운영

설치물은 며칠을 사람 없이 버텨야 한다. 실패해도 멈추지 않게 만들었다.

| 장치 | 동작 |
|---|---|
| 입력 필터 | 접수 시점 차단. 자모 분리·기호 삽입 우회까지 정규화해서 잡는다 |
| canon 스냅샷 | 라운드 확정마다 저장. 서버가 죽어도 이야기가 이어진다 |
| 예산 상한 | 건수·금액 양쪽. 넘으면 조용히 드라이런으로 내려가고 정지화면으로 계속 돈다 |
| 리스테이징 실패 | 원본 체인 프레임으로 폴백 |
| 생성 실패 | 정지화면으로 강등하고 투표는 그대로 진행 |

## 8. 측정된 수치

| 항목 | 값 | 비고 |
|---|---:|---|
| 제출 → 완성 | **47초** | 프리스테이징 적용 전 72초 |
| 3트랙 동시 생성 | 68초 | |
| 클립 1편 원가 | 약 $0.2 | lite · 4초 |
| 누적 사용 | $0.8 / 상한 $15 | 생성 4건 기준 |

배포는 Cloud Run(us-central1). 라운드 드라이버가 백그라운드 스레드라 **CPU 상시 할당**,
상태가 메모리에 있어 **인스턴스 정확히 1개**여야 한다.

## 9. 알려진 문제

| 순위 | 문제 | 영향 |
|---:|---|---|
| 1 | **QR 코드가 없다** | 큰 화면에 45자 URL이 텍스트로만 있다. 아무도 타이핑하지 않는다 |
| 2 | **접수 창 15초가 짧다** | 두 번째 사람이 들어올 시간이 안 된다. 투표가 거의 발생하지 않는다 |
| 3 | **참여자가 많을수록 손해** | 셋이 참여하면 2배 오래 걸리고 채택 확률은 3분의 1 |
| 4 | 탈락 후보가 버려진다 | 생성은 됐는데 아무도 못 본다 |
| 5 | 내 이야기가 어디인지 모른다 | 세 칸 중 어디를 볼지 알려주지 않는다 |
| 6 | 가져갈 것이 없다 | 완결 후 리셋. 저장·공유 수단이 없다 |
| 7 | 완전 무음 | 3분할이라 소리를 못 트는데, 공간 사운드도 없다 |

1·2·5는 각각 30분 이내 작업이다.

## 10. 본 서비스와의 관계

멀티툴은 곁가지가 아니라 **슥의 주장을 라이브로 증명하는 장치**다.

| 슥의 주장 | 멀티툴이 증명하는 것 |
|---|---|
| 원고를 넣으면 영상이 된다 | 참여자가 즉석에서 확인한다 |
| 인기 없어도 먼저 영상화할 수 있다 | 무명의 한 문장이 45초 만에 장면이 된다 |
| 프롬프트 없이 된다 | 참여자는 프롬프트를 배운 적이 없다 |
| 얼굴 일관성을 지킨다 | 6씬 동안 같은 배우가 유지된다 |

### 10.1 독자 거부감 가설을 시험할 유일한 자리

[잠재 사용자 리서치](../Research/잠재%20사용자%20리서치.md)의 최대 리스크는
**독자가 영상화된 캐릭터를 거부한다**는 것이다. 대응 가설 1은
*"읽기 전에 보면 괜찮다"* 인데, 지금까지 검증할 방법이 없었다.

현장의 참여자는 **원작을 읽은 적이 없다.** 침범당할 상상이 아직 없는 상태에서
영상을 만난다. 가설 1의 조건과 정확히 일치한다.

| 관찰 가능한 것 | 가설 |
|---|---|
| 참여자가 캐릭터를 거부하는가 | 가설 1 — 읽기 전 노출 |
| 애니 / 실사 / 웹툰 중 어디에 더 오래 머무는가 | 가설 2 — 양식화된 매체 |
| "내가 쓴 문장"이라는 사실이 수용도를 바꾸는가 | 가설 3 — 작가 정당성 |

**참여자 반응을 기록하면 독자 리서치의 대리 지표가 된다.**
현재 이 관찰은 설계돼 있지 않다. 공개 전에 붙여야 한다.
