# 멀티툴 — 여럿이 함께 만드는 AI 창작 경험

> 개인 창작 도구로 출발해, 두 번의 사용자 반증을 거쳐 **다인 창작 경험**으로 옮겨온 프로젝트.
> 현재 실사용 가능한 시스템이 배포돼 있다.

---

## 1. 프로젝트 개요

| | |
|---|---|
| **기간** | 약 6개월 (저장소 기록 기준) |
| **분야** | 생성형 AI · 공동 창작 · 사용자 경험 |
| **산출물** | 배포된 웹 시스템 2종, 사용자 조사 3회(누적 9명), 설계 문서 |
| **역할** | 기획 · 사용자 조사 · 디자인 · 개발 전 과정 |

### 1.1 문제 정의

웹소설의 영상화가 늘고 있지만, **산업 구조상 인기작만 영상화된다.**
영상화되려면 인기가 있어야 하고, 인기를 얻으려면 영상화가 필요한
**닭-달걀 구조**가 대다수 창작자를 배제한다.

| | |
|---|---:|
| 국내 웹소설 시장 | 1조 3,500억 원 |
| 작품 1편당 500만 원 미만을 버는 작가 | **70.8%** |
| 영상화가 이루어지는 범위 | 사실상 상위 1% |

### 1.2 목표

| | 목표 |
|---|---|
| **평가** | 개인 창작 도구가 실제 창작자에게 작동하는지 평가한다 |
| **분석** | 혼자 만들 때와 여럿이 만들 때 창작 과정이 어떻게 달라지는지 분석한다 |
| **탐색** | 여럿이 AI로 하나의 저작물을 만드는 행위가 성립하는 조건을 탐색한다 |
| **수립** | 다인 AI 창작 경험의 UX 설계 원칙을 수립한다 |

## 2. 연구 방법론

이 프로젝트는 **가설을 세우고 사용자에게 반증당하며 전제를 고쳐온 과정**이다.
기능을 쌓아 올린 것이 아니라 **틀린 전제를 버리며 좁혀왔다.**

### 2.1 1차 — 개인 창작 도구 검증 (솔로툴)

작가가 자기 원고를 직접 영상화하는 프로토타입을 만들고 사용자에게 보여줬다.

| | |
|---|---|
| 참가자 | 2명 — 현역 웹소설 작가 1, 웹소설 다독 독자 1 |
| 방식 | 프로토타입 시연 후 반구조화 인터뷰 |

**발견 1 — 영상화가 상상을 침범한다**

> *"영상화하는 것이 웹소설에 대한 상상력을 발휘하는 데 방해가 될 것 같다."*

커뮤니티에서도 같은 현상이 확인됐다 — *"이 연예인은 이 드라마에는 안 된다"*.
읽은 사람은 **이미 머릿속에서 캐스팅을 끝냈고**, 외부 이미지는 그것을 덮어쓴다.
품질 문제가 아니라 **노출 순서의 문제**였다.

**발견 2 — 창작의 첫 선택은 그림체다**

사용자가 가장 먼저 정한 것은 줄거리도 인물도 아닌 **실사인가 애니메이션인가**였다.

**발견 3 — 기술적 통제권 부족**

| 들은 말 | 깨진 것 |
|---|---|
| "내가 생각했던 주인공 얼굴과 다르다" | 인물 동일성 |
| "입력한 문장과 영상의 싱크가 안 맞는다" | 입력-결과 대응 |
| "더 상세하게 편집할 수 없을까" | 통제권 |

### 2.2 2차 — 기능 보완과 재검증

발견을 반영해 그림체 선택 화면과 세계관 관리 기능을 추가했다.

**발견 4 — 기능을 더할수록 벽이 높아졌다**

> *"그냥 AI로 뭘 만드는 게 어렵다."*

도구를 충실하게 만들수록 **진입이 어려워지는 역설**이 확인됐다.
문제는 기능의 부족이 아니라 **창작의 무게**였다.

### 2.3 방향 전환 — 관찰에 근거한 재설계

전환의 단서는 가정이 아니라 **실재하는 행동**이었다.

> 주변에 **ChatGPT로 여럿이 함께 소설을 써서 웹소설 플랫폼에 게시하는 모임**이 있었다.
> 작가가 아닌 사람들이, 이미 자생적으로 협업 창작을 하고 있었다.

| | 이전 (솔로툴) | 이후 (멀티툴) |
|---|---|---|
| 무게 | 기능이 많은 제작 도구 | 가볍게 즐길 거리 |
| 인원 | 혼자 | **여럿이 같이** |
| 분량 | 한 편을 완성 | 짧게 |
| 대상 | 웹소설 작가 | **예비 창작자 포함** |

### 2.4 3차 — 다인 창작 경험 검증 (멀티툴)

| | |
|---|---|
| 참가자 | 6명 — 산업디자인과 학생, 영어 교사, PD 지망생, 동양화가, 패션업 종사자 |
| 연령 | 20~40대 |
| 표집 근거 | ChatGPT 협업 창작 집단이 20대였던 것을 따랐다 |
| 조건 | **전원 글쓰기가 본업이 아님** |

## 3. UX 문제점 도출

### 3.1 흥미는 확인됐고, 이해가 막았다

| | |
|---|---|
| **재미** | 함께 만드는 행위 자체에는 흥미를 보였다 |
| **어려움** | 사용법을 헷갈려했고, 다음에 무슨 일이 일어나는지 궁금해했다 |

막은 것은 **흥미의 부재가 아니라 이해의 부재**였다.

### 3.2 '어렵다'는 세 번 나왔고 매번 다른 층이었다

| 시점 | 들은 말 | 어려움의 정체 | 상태 |
|---|---|---|---|
| 작가 인터뷰 | "어렵고 필요한가 싶고" | **진입 장벽** — AI가 남의 일 | 해결 |
| 솔로툴 | "AI로 뭘 만드는 게 어렵다" | **조작 부담** — 도구가 무겁다 | 해결 |
| 멀티툴 | 사용법 혼동 · 다음 예측 불가 | **이해 부담** — 구조가 안 보인다 | **미해결** |

한 층을 걷어낼 때마다 다음 층이 드러났다.
남은 것은 기능이 없어서가 아니라 **설명이 없어서** 생기는 어려움이다.

### 3.3 불만의 층위가 올라갔다

| | 솔로툴 | 멀티툴 |
|---|---|---|
| 불만 대상 | 얼굴이 다르다 · 싱크가 안 맞는다 | 기다림 · 규칙 · 공유 · 창작 부담 |
| 층위 | **생성 품질** | **경험 설계** |

인물 동일성과 싱크에 대한 언급이 **사라졌다.**
기술적 해결(리스테이징, 문장 해석)이 실제로 작동했다는 사용자 측 증거다.

### 3.4 도출된 문제 — 창작 국면별

| 국면 | 들은 말 | 문제 |
|---|---|---|
| **착상** | "글 쓰는 게 어렵고 고민된다. 잘 쓰고 싶은데…" | 분량을 줄여도 **창작 부담은 남는다** |
| **착상** | "아이디어를 조금이라도 보태주면 좋겠다" | AI가 **쓰기 단계에는 관여하지 않는다** |
| **작성** | "빨리 하는 사람이 다음 이야기를 선점하는 건지 몰랐다" | **규칙이 보이지 않는다** |
| **대기** | "기다리는 시간이 지루하다" | 대기를 메울 행위가 없다 |
| **소유** | "다 만들어진 영상은 어디로 가는 거냐" | 결과물의 행방이 불투명 |
| **소유** | "이야기가 재미있게 만들어졌는데 공유할 수 있냐" | **밖으로 가져갈 수 없다** |

## 4. UX 개선 방향

### 4.1 구조를 보이게 만든다

가장 시급한 과제다. 참여자가 규칙을 모르면 경쟁인 줄도 모른 채 밀려난다.

| 실행 |
|---|
| 현재 라운드 상태를 상시 표시 — 접수 중 / 생성 중 / 투표 중 |
| 남은 시간과 현재 참여 인원을 함께 노출 |
| 다음에 일어날 일을 미리 예고 |

> 연구 측면에서도 전제 조건이다. 참여자가 자기가 어떤 상황에 있는지 모르면
> **그 상황에 대한 반응을 측정할 수 없다.**

### 4.2 창작 부담을 나눈다

분량을 줄이는 것만으로는 부담이 줄지 않는다. 공개되고 비교되기 때문이다.
현재 AI는 문장 **이후**에만 관여하며, 쓰는 동안에는 아무 역할도 하지 않는다.

| 실행 |
|---|
| 쓰기 단계에 단서 제공 — 앞 장면 기반 키워드, 방향 제안 |
| "잘 쓴 문장"이 아니라 "이어지는 문장"이 목표임을 드러내기 |
| 대기 시간을 다음 문장 구상에 쓰도록 유도 |

공동 창작 관점에서 현재 시스템은 쓰기 국면의 **주도권이 전적으로 사람에게** 있다.
사용자가 그 주도권을 나누기를 요청한 것이다.

### 4.3 기여를 남기고 내보낸다

두 명이 각각 결과물의 행방과 공유 가능성을 물었다.
공유하고 싶다는 것은 그 결과물에 **자기 지분을 느낀다**는 뜻이다.

| 실행 |
|---|
| 완성된 이야기를 URL로 남기기 |
| 기여자 표시 — 어느 장면이 누구의 문장인지 |
| 외부 공유 수단 제공 |

### 4.4 탈락을 설계한다

3명이 참여하면 2명의 문장은 지워진다. 현재는 탈락한 후보의 영상이
**생성되고도 아무에게도 보이지 않는다.**

| 실행 |
|---|
| 발표 시 모든 후보를 짧게 보여준 뒤 채택본 확정 |
| 탈락한 문장도 기록에 남기기 |
| 참여자 수가 늘수록 불리해지는 현재 구조를 재설계 |

> **이 항목은 아직 관측되지 않았다.** 지금까지의 테스트에서 투표 탈락이
> 한 번도 발생하지 않아, 탈락 경험이 참여 동기에 미치는 영향은 미검증이다.

## 5. 구현

사용자 발언에서 출발해 기술 과제가 정의됐다.

| 들은 말 | 구현 | 결과 |
|---|---|---|
| "주인공 얼굴이 다르다" | **리스테이징** — 매 컷 레퍼런스로 얼굴 교정 후 영상 생성 | 후속 테스트에서 언급 소멸 |
| "문장과 영상 싱크가 안 맞는다" | **문장 해석** + 클립 트리밍으로 장면 연결 | 후속 테스트에서 언급 소멸 |
| 대기가 길다 | 선행 처리 · 첫 프레임 선공개 | 72초 → **47초** |

| | |
|---|---:|
| 제출에서 완성까지 | 47초 |
| 동시 3트랙 생성 | 68초 |
| 클립 1편 원가 | 약 $0.2 |
| 서버 | Python 표준 라이브러리, 약 2,800줄 |

배포: Cloud Run · 무인 운영 대비 (입력 필터, 상태 스냅샷, 예산 상한, 단계별 폴백)
